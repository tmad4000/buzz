# Forward to agent (.9 opt-in candidate)

Jacob asked in Buzz P2 at 05:50Z on 2026-11-18 for one-click sends to another orchestrator lane, alongside Send to thread. Root chose two reversible defaults rather than recursive tiers: Paseo DM → P2 (later), and P2 → Paseo DM (now), with a picker for the existing Direct agents rows. This is a separate feature/PR stacked on Direct Agents PR81; it does not change PR81 or rename P2.

Enable **Settings → Appearance → Preferences → Forward to agent** on this device. It defaults off. A delivered message's hover/focus action rail then offers a one-click forward icon for the unambiguous Paseo DM/P2 pair, plus **Forward to agent ▸** for the picker. Icon controls have accessible labels and titles; the action rail remains visible while the picker is open. Only ordinary text-message sources (existing kinds9/40002) are admitted. Pending/system/reaction-only sources are excluded.

## Destinations and default safety

The picker subscribes to the existing mounted sidebar owner's live register tree through a scoped read-only view. It creates no second store, writer, reconciler or relay read loop. Missing, unhydrated or ambiguous owners fail closed. Readiness follows the existing reconciler's decoded/confirmed-new-empty state; unknown, decoding and unreadable heads are unavailable. Disk snapshots never authorize a target, including after failed persistence. Membership and section deletion/rename are preserved. Jacob's recipient-encrypted bundled defaults supply only the section's stable identity, so an edited section label still works; membership always comes from the current view. Other users can use a section named Direct agents. No private channel IDs or keys are hardcoded or copied into source.

Rows must be joined, unarchived DM/stream channels. Forums and the source itself are excluded. Exactly one positively known agent recipient is required from the community agent roster. Unknown humans, empty/unavailable agent rosters and ambiguous agent rows supply no targets or default shortcuts. Peer count and labels alone never establish agent identity. Runtime cards from PR81 optionally supply host chips when that device's runtime-card opt-in is also enabled; cards never turn an agent session UUID into a channel/thread ID.

The one-click DM/P2 defaults additionally require the existing Paseo and Paseo P2/P2 labels, private visibility, exactly two matching members and exactly one opposite lane. Ambiguity, renaming or changed membership removes the shortcut; the explicit picker remains available. No P3 is created. This is a button caption, not a channel rename or priority-contract change.

Live additions/removals update the picker without first opening it. Selecting a destination reads the actual owner tree, and the send callback synchronously rechecks the latest scope, agent roster and live assignment immediately before mutation, after all asynchronous checks. Opening the picker may refresh only the immutable seed section identity query. Before publication it reads writer-pinned source/target metadata and complete rosters. The strict native detail projection joins the complete roster for a true count and required DM participant arrays; metadata and roster use one captured relay/signer context. All four reads carry one expected relay/signer scope, asserted by native detail/member commands, and refuse mismatched member-key sets even at equal counts. A→B→A view changes cancel old intents. Existing metadata-only/nonjoined callers stay compatible (their zero-count legacy detail is never accepted as strict forwarding evidence). Different member sets or open/community-visible destinations require an explicit confirmation naming the target audience and listing members’ names/keys. Unknown/incomplete rosters refuse to send. The confirmation is revalidated; changed members, visibility or target identity require another explicit confirmation, including a change to a same/private audience. Only the unchanged private two-member DM/P2 pair keeps its shortcut. Any supplied confirmation key is compared unconditionally, even when fresh membership becomes the same private pair. A changed key refreshes consent instead of publishing. The relay's existing authorization remains the final membership/write gate. The picker shares a scope-keyed query; disabled forwarding does not mount its queries or signer hooks.

## Publication and source receipt

The picker action puts the sender’s optional one-line note above an explicit source-data envelope, attributes the original author/key and raw event signer, includes a standard `nostr:nevent` reference and the canonical fork backlink, and encloses the literal body in a dynamically sized fence. Third-party/member/agent/email text inside that fence is quoted data, never a new instruction from the forwarding sender. The primary DM↔P2 shortcut always sends reference-only material without a sender note. Cancel, dismiss and successful send clear the picker-owned note; a selected intent captures the note visible for that selection. It does not copy source mention recipients or change/delete/reparent the original. The outgoing target message is an ordinary kind9 message signed by the active user's own client identity. The chosen lane's agent gets an explicit recipient p-tag, including on stream targets, so existing bridge routing applies.

Send-to-thread owner af293993 confirmed the reusable seam: `useSendMessageMutation(channel, identity).mutateAsync(...)`, which returns the target acknowledgement. This feature captures the full target channel, signer and relay; it never calls the composer's private submit method, clears its draft, or overloads `sentFromThreadRootId`. A small additive `expectedScope` argument forces the existing native HTTP path and forwards the already-supported expected relay/signer arguments. A changed native identity/community fails closed. Existing unscoped composer and outbox behavior is preserved.

Scoped action sends skip optimistic cache projection and global timeout-state writes. On ACK they only mark the captured QueryClient's target message/window queries stale, without refetch side effects. `CommunityQueryProvider` is keyed by community/reinitialization/signer/signer epoch, so an old action cannot mutate the replacement cache. Late ACKs save their captured receipt but do not toast/update a replacement view.

Only after acknowledgement does the original in the normal message row and Home Inbox show **Forwarded to P2 ↗** (or the chosen lane's name). It opens the exact acknowledged target event. The marker is a device-local navigation receipt, scoped by relay and signer; it is not a public edit, a reaction or cross-device synced read state. **Other devices will not show Forwarded ↗ in this first slice.** No synced lane is added. It never changes exact-observed receipts, archive, follow-up, thread state or completion.

Concurrent/repeated clicks for the same source/destination/content share one send/receipt. A SHA-256 fingerprint distinguishes edited source text, so forwarding an edit creates a new target message. If publication succeeds but receipt storage fails, the acknowledged ID remains in memory. A retry of the exact captured envelope revision writes only its receipt; a changed note/body is a different revision. Confirmed marker-save failure tells the user not to send again, rather than promising that a note-cleared action can recover the same envelope. ACK dedupe retains every content revision separately, including edit-back and out-of-order concurrent ACKs; the visible line selects one receipt per destination. History is bounded to the latest1000 records per scope. Once the mutation starts, any unconfirmed failure (including malformed native responses and invalid ACKs) explicitly says to check the target before retrying. Preflight failures, explicit relay rejection and confirmed marker-only recovery remain distinct. A process crash before the ACK is received cannot prove delivery. This direct message action does not create an offline outbox entry.
